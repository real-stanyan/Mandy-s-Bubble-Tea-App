## 1. Background

The app shipped on iOS as 1.1.2 build 21 (`62e2765`, 2026-05-08). All RN/JS layer code is platform-agnostic; iOS-specific config lives in `ios/` (generated by `expo prebuild --platform ios`) and a small set of iOS-only plugins / patch scripts (`plugins/embed-square-frameworks.js`, `scripts/fix-square-build-phases.js`). The repo has **no `android/` directory** — Android prebuild has never been run.

Mandy's brick-and-mortar customers ask for an Android version. Day-1 ship target is **EAS-built preview APK distributed via short link / QR**, not Play Store (Play Store production requires a Google Play Console developer account, and a new account from Australia under the post-2023-11 rules requires either (a) Organization verification with ABN/DUNS, 3-7 day Google review, or (b) Personal account + 12-tester closed test + 14 day activity window). Stan will register **Organization account with Mandy's Bubble Tea ABN** in parallel with code work, and Phase B = Play Store production rolls when verification passes.

This spec covers **Phase A only** — code, infrastructure, and EAS distribution. Phase B (Play Store listing / Internal Test track / Production rollout) is sketched but not implemented here.

## 2. Goals

- Full feature parity with iOS 1.1.2 at Day-1: ordering, member QR, Google Sign-In, Square payments, push notifications, cup-label doodle, lottery, multi-cup loyalty.
- All `android/` native code generated by `expo prebuild` is committed (not gitignored), mirroring how `ios/` is managed.
- Zero regression on iOS — no `ios/`, iOS plugin, or `eas.json` ios profile changes.
- EAS preview APK installable on a Google Pixel running stock Android, distributable via short link / QR for customers without Play Store presence.
- Self-contained on the same `com.mandysbubbletea.app` package + same EAS-managed signing keystore as Play Store will eventually use, so Phase B → Phase A users get auto-update takeover without re-login.

## 3. Non-goals

1. **Play Store production listing / Internal Test track / Closed Test track.** Phase B. Phased separately because Stan needs Google Play Console Org account verification (3-7 days external dependency).
2. **Google Pay merchant enablement.** Stan checks Square Dashboard status during implementation; if not enabled, Day-1 falls back to Card Entry sheet, Google Pay path lands in v1.2.1.
3. **Owner Widget Android port.** Separate repo `mandys_bubble_tea_widget` is iOS-only WidgetKit. Android widget = Glance/AppWidget, separate project, separate Phase.
4. **Tablet form factor.** `app.json` `ios.supportsTablet: false`; Android default phone-first. No tablet smoke required.
5. **OEM-specific battery saver workarounds.** Pixel = stock Android. If a customer with Xiaomi MIUI / Samsung OneUI hits FCM delivery quirks post-launch, address as v1.2.1 follow-up.
6. **OTA update channel.** Phase A APK updates require manual reinstall (new EAS URL). Phase B Play Store auto-updates.
7. **iOS code changes.** This spec touches RN/JS only where a `Platform.OS === 'android'` branch is needed. iOS behavior must be byte-identical pre/post.
8. **Backend / Supabase / Square server changes.** Server side is platform-blind; all existing routes accept the same payloads regardless of client.

## 4. Architecture

### 4.1 What changes / what doesn't

**Unchanged (zero diff):**
- `ios/*` (iOS native project — generated but committed)
- `plugins/embed-square-frameworks.js` (uses `withDangerousMod` locked to `'ios'`; Android prebuild silently skips)
- `scripts/fix-square-build-phases.js` (iOS xcodeproj only)
- All JS/TS code in `lib/`, `hooks/`, `store/`, `components/` except the small Platform.OS branches enumerated in §6.
- All API routes in companion `mandys_bubble_tea` web repo (Supabase + Square server is platform-blind)

**New directory:**
- `android/` — generated by `expo prebuild --platform android`. Committed wholesale. `.gitignore` carves out `android/build/`, `android/app/build/`, `android/.gradle/`, `android/local.properties`.

**Modified files (RN/JS layer):**
- `app.json` — Android plugin config (`@react-native-google-signin/google-signin` Android section; `expo-notifications` color etc), `android.googleServicesFile: "./google-services.json"` reference, version bump 1.1.2 → 1.2.0
- `eas.json` — new `preview-android` profile (apk build type, internal distribution); existing iOS profiles untouched
- `hooks/` (TBD — payment + sign-in hooks): `Platform.OS === 'android'` branches per §6
- `app/sign-in.tsx` (or wherever Apple Sign-In is mounted): hide Apple Sign-In on Android per §6.2
- `app/checkout.tsx`: Google Pay / Card Entry branch on Android per §6.1
- Notification setup site (likely `lib/notifications.ts` or `app/_layout.tsx`): Android channel registration per §6.3
- `lib/notifications.ts` (or where push permission is requested): Android 13+ `POST_NOTIFICATIONS` runtime perm

**New files:**
- `google-services.json` (Firebase Android config; committed because EAS Build CI needs it; **does not contain secrets** — public-safe identifiers only)
- `docs/distribution/android-customer-install.md` (顾客 1-page 安装指南，中英双语)

**Possibly new (depending on implementation):**
- 1-2 jest tests for Platform.OS branch coverage

## 6. Android-specific code branches

Locations may shift during implementation; below is the contract, not the line-numbered diff.

### 6.1 Payments — `app/checkout.tsx` + payment hook

```tsx
if (Platform.OS === 'ios') {
  // existing Apple Pay path via SQIPApplePay
} else if (Platform.OS === 'android') {
  if (GOOGLE_PAY_ENABLED) {
    SQIPGooglePay.requestGooglePayNonce(...)
  } else {
    SQIPCardEntry.startCardEntryFlow(...)
  }
}
```

`GOOGLE_PAY_ENABLED` sourced from `EXPO_PUBLIC_SQUARE_GOOGLE_PAY_ENABLED` (build-time env, set after P0 #3 check). Default `false` → Card Entry sheet, which works with or without Square Google Pay merchant enabled.

### 6.2 Sign-in — `app/sign-in.tsx` (or Account page sign-in section)

iOS shows both "Continue with Apple" and "Continue with Google". Apple's App Store rule §4.8 requires iOS apps with third-party SSO to also offer Sign in with Apple; Android has no such rule, so Android shows only "Continue with Google".

```tsx
{Platform.OS === 'ios' && <AppleSignInButton onPress={signInWithApple} />}
<GoogleSignInButton onPress={signInWithGoogle} />
```

### 6.3 Push permission — `lib/notifications.ts` (or wherever first push request happens)

```ts
// Android 13 (API 33+) requires runtime POST_NOTIFICATIONS permission.
// expo-notifications requestPermissionsAsync handles the prompt automatically
// on Android 13+; on Android <13, the manifest permission is granted at install.
const { status } = await Notifications.requestPermissionsAsync()
if (status !== 'granted') {
  // Show in-app explainer: "Push notifications are off. You won't get a ping
  // when your drink is ready. Open Settings to enable them." → Linking.openSettings()
}
```

### 6.4 Notification channel — Android-only, called at app startup

```ts
if (Platform.OS === 'android') {
  await Notifications.setNotificationChannelAsync('default', {
    name: 'Order updates',
    importance: Notifications.AndroidImportance.HIGH,
    vibrationPattern: [0, 250, 250, 250],
    lightColor: '#C43A10',
    sound: 'default',
  })
}
```

iOS ignores `setNotificationChannelAsync` (no-op). Android **requires** it before any FCM message can render with a heads-up notification — otherwise messages arrive silently.

### 6.5 StatusBar / SafeArea

`app.json` already has `android.edgeToEdgeEnabled: true`. RN content fills the screen including under the status bar. Existing `react-native-safe-area-context` wrappers handle this cross-platform. The root `_layout.tsx` must declare `<StatusBar style="dark" />` (or `auto` if light/dark theme switching exists) to ensure Android status bar icon contrast renders correctly on cream background — iOS reads this; Android needs it more rigidly.

### 6.6 Back gesture

`app.json` already has `android.predictiveBackGestureEnabled: false` (avoid Android 14 predictive back animation conflicting with Expo Router stack transitions). `expo-router` Stack already handles `BackHandler` for system back → pops navigation. Modal sheets need manual verification at T11 — if any modal exits the app on system back instead of dismissing, add a per-modal `BackHandler` listener in T8.

## 7. Task slicing (T1-T12)

Implemented as separate atomic tasks following subagent-driven-development pattern. Each task ends with a verifiable "done" state. The companion plan doc (writing-plans output) will expand each into TDD red→green→quality-review.

| # | Task | Owner | Done |
|---|------|-------|------|

## 8. Testing strategy

### 8.1 Layer 1 — unit (jest)

Existing ~36 jest tests stay green throughout. T8 adds 1-2 tests mocking `Platform.OS = 'android'` to verify payment hook and sign-in renderer pick the Android branch.

Target: ~38/38 pass at T11 end.

### 8.2 Layer 2 — per-task verify (Section 7 "done" column)

Each task ends with a Pixel real-device check before declaring "done". Pre-T10 tasks use `expo run:android` (Metro-bundled dev client); T10+ uses installed EAS APK.

### 8.3 Layer 3 — T11 full real-line smoke (10 cases)

Run on the same Pixel after EAS APK install. All 10 must pass. Any failure blocks T12.

1. **Cold start + persisted session** — install APK, first launch, kill, relaunch, Supabase session persists (no re-login).
2. **Google Sign-In new user flow** — sign out, "Continue with Google", native picker, idToken → Supabase auth → `auth.users` row created.
3. **Multi-cup cart + checkout math** — 3+ drinks with modifiers; cart subtotal + PLATFORM_FEE 0.5% correct.
4. **Payment success** — Google Pay sheet (if enabled) OR Card Entry sheet (fallback); sandbox or production charge succeeds; order row in Supabase.
5. **Welcome discount** — new user shows welcome 30% off badge in 3 expected locations; applies once and is consumed.
6. **Loyalty multi-cup reward stepper** — with 18+ stars and 3 cups in cart, stepper max=2; selecting 2 → 2 free + 1 paid; Square Dashboard shows 2 REDEEM_REWARD events.
7. **Order READY push** — backend marks order READY → FCM push → Pixel heads-up notification with vibration → tap → opens order detail screen.
8. **Cup-label doodle + AI** — manual draw OR photo upload OR "Surprise me" AI → `cup_label_jobs` row created with correct `doodle_source` → ZD410 printer-client prints (existing printer-client path untouched).
9. **Lottery prize** — if active lottery, winning draw shows applied prize in checkout, Google Pay sheet/card entry shows discounted total; `lottery_redemption` row written; Square order total matches charged amount.
10. **App Link deep link** — `https://mandybubbletea.com/menu` clicked from Chrome opens the app to menu directly (no browser fallback); `adb shell pm get-app-links` confirms `verified`.

## 9. Distribution

### 9.1 Phase A — EAS preview APK short link

After T10 green build, fetch APK URL:

```bash
eas build:list --platform android --limit 1 --json | jq -r '.[0].artifacts.buildUrl'
```

Generate QR PNG with `qrencode` and save to `~/Downloads/mandys-android-v1-install-qr.png`. Write `docs/distribution/android-customer-install.md` 1-page bilingual install guide:

1. Scan QR → browser downloads APK
2. Settings → Security → "Install unknown apps" → allow Chrome/Files once
3. Open APK → Install → Launch
4. Update flow: when a new EAS build URL is published, replace the QR; customers must manually re-download (Phase B replaces this with auto-update)

Stan posts QR at Mandy's counter + share with Mandy's Android-using regulars.

### 9.2 Phase B — Play Store (separate spec, post-verification)

Once Google Play Console Organization verification passes (3-7 day external dependency), Phase B starts:

1. `eas submit --profile production --platform android` → uploads AAB to Play Console
2. Play Console: configure Internal Test track with Stan + Mandy + 5-10 regulars (transition from Phase A APK users)
3. After 14 day stability window: Closed Test → Production rollout
4. Same `com.mandysbubbletea.app` package + same EAS-managed signing keystore means Play Store version installs over Phase A APK with no data loss / re-login (Android upgrade install semantics).

## 10. Abort criteria

Any of the following triggers a Stan conversation, not silent continuation:

- **T2:** FCM token retrieval fails despite correct `google-services.json` placement → Firebase setup issue, possibly switch to "Day-1 no push, push as v1.2.1" backup plan.
- **T4:** `react-native-square-in-app-payments` v2.0.0 Android Gradle config broken → evaluate (a) switching to official Square Mobile Payments SDK fork, (b) WebView checkout fallback temporarily.
- **T5:** Google Pay merchant enabled but nonce retrieval fails → fallback to Card Entry only, Google Pay reschedules to v1.2.1.
- **T11:** More than 3 of 10 smoke cases fail → systemic Android bug; pause T12 and revisit T8 Platform.OS branch logic.

## 11. Rollback

Phase A code lives on `feat/android-port` branch. If a critical issue surfaces after T12 distribute:

1. EAS APK URL stops being shared; Stan can also remove the build from EAS Dashboard so the artifact 404s.
2. The QR poster pulled from Mandy's counter.
3. Stan informs the 1-2 real users to uninstall.
4. Branch stays alive; fix in a follow-up commit; re-build EAS APK; re-distribute new QR.

No iOS code is touched, so iOS 1.1.2 production users see zero impact.
